1. What does “dunder” mean?

Dunder is short for “double underscore”. A name such as __len__ is called a special method name. Python reserves many of these names for its data model.

The important idea is that you normally do not write x.__len__(). You write len(x). Python sees the operation and uses the protocol that your class provides.

Your code
len(cart)
Python protocol
length
Special method
__len__
Result
integer
class Cart:
    def __init__(self):
        self.items = ["book", "pen", "bag"]

    def __len__(self):
        return len(self.items)

cart = Cart()
print(len(cart))
# 3

When len(cart) runs, Python asks the object's type for the length protocol. Your __len__ supplies that behavior.

Common mistake: special methods are not normal callbacks that Python finds by searching the instance dictionary. For many built-in operations, Python looks on the type. That is one reason changing x.__len__ on a single instance does not behave like changing a normal instance method.

2. Object lifecycle: __new__, __init__, and __del__

First: creation versus initialization

These two words sound similar but mean different things. __new__ is involved in getting an object instance. __init__ receives that instance and initializes its state.

class User:
    def __new__(cls, name):
        print("1 - __new__")
        obj = super().__new__(cls)
        return obj

    def __init__(self, name):
        print("2 - __init__")
        self.name = name

u = User("Harsh")
# 1 - __new__
# 2 - __init__

Think of it like buying a notebook. __new__ gets the physical notebook. __init__ writes your name and sets up the pages. Most classes only need __init__; __new__ becomes useful for immutable types, factories, caching, and advanced construction.

__new__ in an immutable type

Immutable objects cannot be changed after creation, so values sometimes need to be supplied during __new__.

class PositiveInt(int):
    def __new__(cls, value):
        if value < 0:
            raise ValueError("must be positive")
        return super().__new__(cls, value)

x = PositiveInt(10)
print(x)  # 10

__del__

__del__ is a finalization hook. It may run when an object is being finalized, but it is not the right place for critical cleanup. Python's garbage collection and interpreter shutdown can make its timing complicated.

Use this rule: if something must be released reliably, use a context manager such as with open(...), not __del__.
Exam trap: __new__ returns the object; __init__ should return None. If __new__ does not return an instance of the class being constructed, normal initialization can be skipped.

3. Representation: __str__, __repr__, __format__

There are two common questions: “How should this object look to a user?” and “How should this object look to a developer debugging it?”

__str__

Human-friendly text. Used by str(x) and normally by print(x).

__repr__

Developer-oriented representation. Used by repr(x) and often visible inside containers.

__format__

Controls formatting when a value appears in a format expression such as f"{x:.2f}".

__bytes__

Controls bytes(x).

class Money:
    def __init__(self, amount):
        self.amount = amount

    def __str__(self):
        return f"₹{self.amount:.2f}"

    def __repr__(self):
        return f"Money({self.amount!r})"

m = Money(125.5)
print(m)
print(repr(m))

# ₹125.50
# Money(125.5)

Notice the difference. str(m) answers “what should a person see?” while repr(m) answers “what representation helps me understand the object?”

Fallback: if a class does not define __str__, Python can fall back to __repr__. A useful __repr__ therefore improves debugging even when you never write __str__.

4. Equality, ordering, and hashing

By default, two separate user-defined objects are usually compared by identity. You can define value-based equality with __eq__.

class Point:
    def __init__(self, x, y):
        self.x = x
        self.y = y

    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented
        return self.x == other.x and self.y == other.y

print(Point(2, 3) == Point(2, 3))
# True

Returning NotImplemented is different from returning False. It tells Python that your method does not know how to compare those types, so Python may try the other operand's implementation or use the normal fallback.

__hash__

Hashing matters for sets and dictionary keys. If a == b, their hashes must agree. That is why mutable objects need care: if a value used for equality changes after insertion into a set, the set can no longer behave correctly.

class User:
    def __init__(self, user_id):
        self.user_id = user_id

    def __eq__(self, other):
        return isinstance(other, User) and self.user_id == other.user_id

    def __hash__(self):
        return hash(self.user_id)

users = {User(10)}
print(User(10) in users)
# True

Operators are another part of the data model. If you define the right special method, your class can participate in normal Python expressions.

class Money:
    def __init__(self, amount):
        self.amount = amount

    def __add__(self, other):
        if not isinstance(other, Money):
            return NotImplemented
        return Money(self.amount + other.amount)

    def __repr__(self):
        return f"Money({self.amount})"

print(Money(100) + Money(50))
# Money(150)

Reflected operators

There is also a right-hand family: __radd__, __rsub__, __rmul__, and so on. These matter when the left operand cannot handle the other type.

class Score:
    def __init__(self, value):
        self.value = value

    def __radd__(self, other):
        return other + self.value

s = Score(10)
print(5 + s)
# 15

For in-place operators, Python may use methods such as __iadd__. A mutable object can modify itself, while an immutable object can return a new object.

Do not blindly return False for an unsupported type. NotImplemented gives Python a chance to try the other operand's protocol.

class Playlist:
    def __init__(self, songs):
        self.songs = list(songs)

    def __len__(self):

        return self.songs[index]

Slices

__getitem__ can receive a slice object, so x[1:4] can be handled by checking the key.

class Numbers:
    def __init__(self, values):
        self.values = list(values)

    def __getitem__(self, key):
        return self.values[key]

n = Numbers([10, 20, 30, 40])
print(n[1:3])
# [20, 30]

7. Iteration: __iter__ and __next__

A for loop asks for an iterator. An iterator supplies values one at a time and raises StopIteration when it is finished.

class CountUp:
    def __init__(self, stop):
        self.current = 0
        self.stop = stop

    def __iter__(self):
        return self

    def __next__(self):
        if self.current >= self.stop:
            raise StopIteration
        value = self.current
        self.current += 1
        return value

for n in CountUp(3):
    print(n)
# 0
# 1
# 2

The important distinction is that an iterable can produce an iterator, while an iterator remembers its current position and implements __next__.

for loop
iter(obj)
next(iterator)
StopIteration

Async iteration

Async code has corresponding protocols such as __aiter__ and __anext__, used by async for. They are the same idea applied to asynchronous data production.

8. Callable objects: __call__

Normally, f() means “call function f”. But classes can also make their instances callable.

class Multiplier:
    def __init__(self, factor):
        self.factor = factor

    def __call__(self, value):
        return value * self.factor

double = Multiplier(2)
print(double(7))
# 14

After defining __call__, double(7) becomes a natural interface for an object that behaves like a function.

Useful real-world pattern

Callable objects are useful for validators, configuration-based processors, machine-learning models, retry policies, and stateful callbacks because the object can remember configuration in attributes.

class MinimumLength:
    def __init__(self, minimum):
        self.minimum = minimum

    def __call__(self, text):
        return len(text) >= self.minimum

valid_name = MinimumLength(3)
print(valid_name("Hi"))
print(valid_name("Harsh"))
# False
# True

9. Context managers: __enter__ and __exit__

The with statement is a protocol. A context manager prepares something when entering and cleans it up when leaving.

class Demo:
    def __enter__(self):
        print("enter")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("exit")
        return False

with Demo() as d:
    print("inside")

# enter
# inside
# exit

Conceptually, Python ensures that the exit hook is called even when the block raises an exception. The three arguments supplied to __exit__ describe an active exception; if there is no exception they are None.

Suppressing an exception

class IgnoreErrors:
    def __enter__(self):
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        return True

with IgnoreErrors():
    raise ValueError("ignored")

print("still running")
# still running
Be careful: returning True from __exit__ suppresses the exception. Most context managers should return False or None unless suppression is intentional.

10. Attribute trapping — the part you should understand deeply

“Attribute trapping” means intercepting ordinary attribute operations so your class can observe, validate, redirect, or synthesize them.

There are four especially important hooks:

  • __getattribute__ — runs for essentially every normal attribute read.
  • __getattr__ — fallback called when normal lookup fails.
  • __setattr__ — intercepts normal attribute assignment.
  • __delattr__ — intercepts normal attribute deletion.
The key distinction: __getattribute__ is the gate you pass through when reading an attribute. __getattr__ is a fallback after ordinary lookup fails. They are not interchangeable.

10.1 Start with normal lookup

class Person:
    def __init__(self):
        self.name = "Harsh"

p = Person()
print(p.name)

It feels simple: “look inside p and get name”. But Python's object model has a lookup process involving the class, the instance dictionary, inheritance, and descriptors.

p.name
attribute lookup
class / descriptor / instance data
value returned

10.2 __getattribute__: intercept every read

class Person:
    def __init__(self):
        self.name = "Harsh"

    def __getattribute__(self, name):
        print("Reading:", name)
        return object.__getattribute__(self, name)

p = Person()
print(p.name)
# Reading: name
# Harsh

When p.name is evaluated, your override gets the string "name". You can log it, redirect it, or enforce a policy. But eventually you normally delegate to object.__getattribute__ so Python can perform the normal lookup.

10.3 Why naive implementations recurse forever

class Person:
    def __init__(self):
        self.name = "Harsh"

    def __getattribute__(self, name):
        print("Reading", self.name)  # BAD
        return object.__getattribute__(self, name)

Why is self.name bad inside __getattribute__? Because reading self.name calls __getattribute__ again. That second call tries to read self.name, which calls it again, and so on until Python raises RecursionError.

The safe escape hatch is to use the base implementation directly:

object.__getattribute__(self, "name")
Rule to remember: inside __getattribute__, do not use self.some_attribute unless you deliberately want to trigger the trap again. Use object.__getattribute__(self, "some_attribute") when you need safe normal lookup.

10.4 Practical example: logging attribute reads

class LoggedObject:
    def __getattribute__(self, name):
        print(f"READ {name}")
        return object.__getattribute__(self, name)

class User(LoggedObject):
    def __init__(self, name, age):
        self.name = name
        self.age = age

u = User("Harsh", 22)
print(u.age)
# READ age
# 22

Because __getattribute__ is inherited, the logging behavior applies to the subclass too.

10.5 __getattr__: a fallback, not the first gate

class Settings:
    def __init__(self):
        self.theme = "dark"

    def __getattr__(self, name):
        return f"{name} is not configured"

s = Settings()
print(s.theme)
print(s.language)
# dark
# language is not configured

For s.theme, normal lookup succeeds, so __getattr__ is not needed. For s.language, normal lookup fails, so Python gives __getattr__ a chance to produce a value.

10.6 __setattr__: intercept assignment

class Person:
    def __setattr__(self, name, value):
        if name == "age" and value < 0:
            raise ValueError("age cannot be negative")
        object.__setattr__(self, name, value)

p = Person()
p.age = 22
print(p.age)
# 22

When Python evaluates p.age = 22, it can call p.__setattr__("age", 22). The override validates the value and delegates the actual storage to the base implementation.

The recursion trap

def __setattr__(self, name, value):
    self.__dict__[name] = value

# This version can work, but if you write:
# self.__dict__ = something
# you are assigning an attribute again and can trigger the trap.

For simple cases, object.__setattr__(self, name, value) is the clearest delegation method.

10.7 __delattr__: intercept deletion

class Locked:
    def __init__(self):
        self.name = "Harsh"

    def __delattr__(self, name):
        if name == "name":
            raise AttributeError("name cannot be deleted")
        object.__delattr__(self, name)

x = Locked()
del x.name
# AttributeError

10.8 Putting all four together

class Trapped:
    def __init__(self):
        self.name = "Harsh"

    def __getattribute__(self, name):
        print("GET", name)
        return object.__getattribute__(self, name)

    def __getattr__(self, name):
        print("FALLBACK", name)
        return "missing"

    def __setattr__(self, name, value):
        print("SET", name, value)
        object.__setattr__(self, name, value)

    def __delattr__(self, name):
        print("DELETE", name)
        object.__delattr__(self, name)

x = Trapped()
print(x.name)
print(x.age)
x.age = 22
del x.age

Trace it mentally. Creating x calls __setattr__ for name. Reading x.name calls __getattribute__ and succeeds. Reading x.age enters __getattribute__, fails normal lookup, then reaches __getattr__. Assigning x.age uses __setattr__. Deleting it uses __delattr__.

10.9 Why attribute trapping is useful

Validation

Reject invalid assignments before they reach object state.

Lazy values

Compute a value only when code first asks for it.

Logging

Observe reads and writes for debugging or auditing.

Proxies

Forward unknown attributes to another object or service.

Do not overuse it. Attribute hooks can make code difficult to understand. Prefer normal properties, methods, or descriptors when they express the intention more clearly.

11. Descriptors: the machinery behind many “magic” attributes

A descriptor is an object that defines methods such as __get__, __set__, or __delete__. Descriptors control what happens when an attribute is accessed.

This sounds abstract, so start with a tiny example.

class LoggedValue:
    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, instance, owner):
        if instance is None:
            return self
        print("GET", self.name)
        return instance.__dict__.get(self.name)

    def __set__(self, instance, value):
        print("SET", self.name, value)
        instance.__dict__[self.name] = value

class User:
    age = LoggedValue()

u = User()
u.age = 22
print(u.age)

The class attribute age is not a normal number. It is a descriptor. When Python sees u.age, the descriptor can control the operation.

Data versus non-data descriptors

A descriptor implementing __set__ or __delete__ is a data descriptor. A descriptor implementing only __get__ is a non-data descriptor. This distinction matters because it affects precedence during attribute lookup.

data descriptor
instance dictionary
non-data descriptor
class attribute / MRO

This is one reason a property can enforce validation even when an instance dictionary contains a tempting-looking value: a property is a data descriptor when it defines a setter.

__set_name__

Python calls __set_name__ when the descriptor is assigned as part of class creation. It lets the descriptor learn the attribute name automatically.

class Field:
    def __set_name__(self, owner, name):
        self.name = name

    def __get__(self, instance, owner):
        if instance is None:
            return self
        return instance.__dict__.get(self.name)

    def __set__(self, instance, value):
        instance.__dict__[self.name] = value

class User:
    username = Field()
    email = Field()

u = User()
u.username = "harsh"
print(u.username)
# harsh

The same descriptor class can now be reused for different fields without hard-coding the names.

12. Why normal methods work: functions are descriptors

This is one of Python's most useful internal connections. A function stored on a class can act as a descriptor.

class Person:
    def greet(self):
        return "hello"

p = Person()
print(p.greet())

You write p.greet(), but the function was stored on Person. Python's descriptor machinery turns the function into a bound method, supplying p as the first argument.

That is why this:

p.greet()

is conceptually related to retrieving the function from the class and binding the instance to it. The exact descriptor protocol is more precise than simply saying “Python inserts self”, but this mental model is excellent for learning.

staticmethod changes binding

class Math:
    def normal(self, x):
        return x * 2

    @staticmethod
    def double(x):
        return x * 2

m = Math()
print(m.double(5))
# 10

The static method wrapper prevents the normal instance binding behavior. No self is automatically supplied.

13. Class decorators — from syntax to real implementation

A decorator is a callable that receives something and returns a replacement or modified version of it. A class decorator receives a class.

13.1 The syntax transformation

@add_feature
class Person:
    pass

means approximately:

class Person:
    pass

Person = add_feature(Person)

This is the first thing to memorize. The decorator runs after the class body has created the class object.

13.2 A tiny class decorator

def add_greeting(cls):
    def greet(self):
        return f"Hello, {self.name}!"

    cls.greet = greet
    return cls

@add_greeting
class Person:
    def __init__(self, name):
        self.name = name

p = Person("Harsh")
print(p.greet())
# Hello, Harsh!

The decorator receives Person, adds a method, and returns the same class.

13.3 A decorator that wraps an existing method

from functools import wraps

def log_methods(cls):
    original = cls.run

    @wraps(original)
    def wrapped(self, *args, **kwargs):
        print("RUNNING", cls.__name__)
        return original(self, *args, **kwargs)

    cls.run = wrapped
    return cls

@log_methods
class Job:
    def run(self):
        return "done"

print(Job().run())
# RUNNING Job
# done

functools.wraps helps preserve useful metadata such as the wrapped function's name and documentation.

13.4 Decorators with arguments

def tag(label):
    def decorate(cls):
        cls.tag = label
        return cls
    return decorate

@tag("admin")
class User:
    pass

print(User.tag)
# admin

Here tag("admin") first creates a decorator. That decorator then receives the class.

13.5 Multiple decorators and order

@outer
@inner
class Demo:
    pass

is equivalent to:

class Demo:
    pass

Demo = inner(Demo)
Demo = outer(Demo)

So decorators are applied from the bottom upward. This becomes important when two decorators both modify or replace the class.

PRA trap: if you see three decorators, do not read them from top to bottom as “first, second, third”. Write the equivalent assignments and evaluate them from the bottom decorator outward.

13.6 Class decorator versus metaclass

A class decorator usually modifies a class after the class has been created. A metaclass controls the class creation process itself. Use a decorator when a normal transformation is enough; use a metaclass only when you genuinely need class-creation-level control.

14. Important built-in decorators

@classmethod

A class method receives the class as its first argument, conventionally named cls. It is useful for alternate constructors and operations involving class-level state.

class User:
    def __init__(self, name):
        self.name = name

    @classmethod
    def guest(cls):
        return cls("Guest")

u = User.guest()
print(u.name)
# Guest

Because it receives cls, a subclass can inherit the method and still construct the subclass when the method uses cls(...).

@staticmethod

A static method receives no automatic self or cls. It is simply a function stored in the class namespace because the function conceptually belongs with the class.

class Temperature:
    @staticmethod
    def c_to_f(c):
        return c * 9 / 5 + 32

print(Temperature.c_to_f(0))
# 32.0

@property

A property makes method-like logic look like an attribute. This is excellent for validation and computed values.

class Celsius:
    def __init__(self, value):
        self._value = value

    @property
    def value(self):
        return self._value

    @value.setter
    def value(self, new):
        if new < -273.15:
            raise ValueError("below absolute zero")
        self._value = new

c = Celsius(20)
c.value = 25
print(c.value)
# 25

Under the surface, property is a descriptor. That connects decorators, descriptors, and attribute trapping into one idea.

@abstractmethod

from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self):
        pass

class Circle(Shape):
    def __init__(self, r):
        self.r = r

    def area(self):
        return 3.14159 * self.r ** 2

# Shape() -> TypeError
# Circle(2) -> allowed

The abstract method creates a contract. A concrete subclass must implement the required operation before it can be instantiated.

@dataclass

@dataclass is a class decorator that can generate common methods such as __init__, __repr__, and __eq__ based on declared fields.

from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p = Point(2, 3)
print(p)
# Point(x=2, y=3)

This is a useful real-world example of a decorator doing substantial class transformation for you.

Other useful decorators

A custom metaclass can customize class creation.

class Meta(type):
    def __new__(mcls, name, bases, namespace):
        print("Creating class:", name)
        return super().__new__(mcls, name, bases, namespace)

class User(metaclass=Meta):
    pass

# Creating class: User

The metaclass receives the class name, base classes, and namespace while the class object is being created.

Do not jump to metaclasses too early. Most problems that look like they need a metaclass can be solved with a normal class, descriptor, decorator, or __init_subclass__.

__init_subclass__ — often the simpler alternative

class Plugin:
    registry = []

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        Plugin.registry.append(cls.__name__)

class AudioPlugin(Plugin):
    pass

class VideoPlugin(Plugin):
    pass

print(Plugin.registry)
# ['AudioPlugin', 'VideoPlugin']

__init_subclass__ lets a base class react whenever a subclass is created without introducing a custom metaclass.

It is better to understand each family than to memorize an enormous alphabetized list without context.

17. Practice the concepts instead of memorizing them

Trap 1: __getattribute__ versus __getattr__

class Demo:
    def __getattribute__(self, name):
        print("GET", name)
        return object.__getattribute__(self, name)

    def __getattr__(self, name):
        print("MISSING", name)
        return 99

x = Demo()
print(x.answer)

Ask yourself: which hook runs first? Answer: __getattribute__. Only after normal lookup fails can __getattr__ supply the fallback.

Trap 2: class attribute versus instance attribute

class User:
    role = "viewer"

u = User()
u.role = "admin"

print(User.role)
print(u.role)
# viewer
# admin

The assignment creates an instance attribute that shadows the class attribute for that instance. It does not change User.role.

Trap 3: method binding

class A:
    def show(self):
        return "A"

a = A()
print(a.show())
print(A.show(a))
# A
# A

These are two views of the same underlying function: one obtains a bound method from the instance; the other passes the instance explicitly.

Trap 4: cooperative multiple inheritance

class A:
    def f(self):
        return ["A"]

class B(A):
    def f(self):
        return super().f() + ["B"]

class C(A):
    def f(self):
        return super().f() + ["C"]

class D(B, C):
    def f(self):
        return super().f() + ["D"]

print(D().f())
# ['A', 'C', 'B', 'D']

Do not interpret super() as “call my parent”. It means “continue lookup after this class in the method-resolution order”. For D, the relevant chain is D → B → C → A.

Trap 5: decorator order

def first(cls):
    cls.value = cls.value + 1
    return cls

def second(cls):
    cls.value = cls.value * 2
    return cls

@first
@second
class Demo:
    value = 3

print(Demo.value)
# 7

First second changes 3 to 6. Then first changes 6 to 7.

Recommended learning order: dunder basics → lifecycle → representation → operators → containers → iteration → callable/context protocols → attribute trapping → descriptors → decorators → metaclasses. This order builds the machinery gradually instead of throwing all of Python's internals at you at once.
